# 验证、导出与续做

在建立验收范围时阅读一次；发布前或处理测试受阻时再次按需查阅。检查规模与本次风险匹配，已通过的检查只有在相关实现改变或出现新证据时才重跑。

## 证据分层

| 层次 | 可证明什么 | 不能替代什么 |
| --- | --- | --- |
| 资源/静态检查 | 路径、数据、图集、字体及配置问题 | 实际渲染与交互 |
| 引擎导入/无头运行 | 解析、导入、部分运行时与逻辑规则 | 灯光、窗口输入、听感、真实 GPU 性能 |
| 逻辑/场景测试 | 边界规则、状态与回归路径 | 玩法是否有趣、画面是否好看 |
| 实际运行与操作 | 输入、反馈、导航、连续动画、流程阻塞 | 未走过的分支和旧档兼容 |
| 音频试听与视觉对照 | 当前条件下的观感、混音与参考一致性 | 所有硬件与所有场景 |
| 导出产物启动 | 分发版本能否启动、资源是否齐全 | 源码运行结果不能代替这一层 |

每项记录通过、失败或未验证以及可查证的命令/日志/截图/录音路径。不要把“启动命令已发出”当成功，也不要把因权限失败或被用户中止的调用记为通过。

## 首版真实游玩路线

使用干净、隔离的测试存档，以正常输入从标题进入，完成教学、探索、核心操作、成长/装备或编队、区域目标、挑战、奖励领取和阶段结局；再保存、退出进程、启动并继续。默认捕捉 RPG 额外走投失/撞墙、普通捕捉失败、印记球成功、满队伍、全队失败恢复等路径。

检查无存档继续、暂停与返回标题、设置保存、输入焦点、长中文文本、窗口变化和连续游玩。缺少 UI 自动化时可使用工程内受控测试入口覆盖运行时规则，但须区分直接调用内部函数与真正验证了玩家输入；不能对后者作虚假声明。

视觉检查包含代表区域、昼夜和天气、连续角色/宠物移动、战斗及主要 UI。性能在记录的硬件、分辨率、渲染器和画质下采样代表路线的帧时间及波动；单张截图/瞬时 FPS 不支持“稳定 60 帧”。按证据定位灯光、粒子、绘制、脚本瓶颈后优化。

## 阻塞处理

遇到缺少引擎、导出模板、素材工具或 GUI 权限，先确认真实原因，再继续独立可做的部分。同一权限拒绝不能反复包装重试；若需要用户行动，简短说明具体受阻操作、来源和完成它所需条件。普通可逆的实现和检查不人为增设批准关卡。

未能运行画面/声音或导出时可交付已完成的源码与证据，但明确标为阶段交付，列出尚缺的验收。不能承诺 skill 会在会话结束后自己唤醒、自动规避权限或保证一次生成商业级成品。

## 导出与版本对应

使用实际引擎支持的导出预设与模板，检查导出日志、退出状态和产物是否新生成。记录构建时间、引擎版本、目标平台、对应提交（若有）、有无未提交改动，并对实际参与构建的源码/资源和产物记录必要的哈希或清单；不把整个缓存目录当源码。

从独立发布目录启动最终产物，验证标题、进入游戏、关键修复、存档读写、音频与退出；确认不依赖源码目录中的漏打包文件。构建后若修改运行资源或代码，旧产物不能继续标为最新版；重新导出相关平台再复验。保留已知可用版本，避免更新失败后无可玩包。

项目使用 Git 时检查工作树及用户修改，只提交本轮相关且经过验证的文件；避免纳入导入缓存、敏感配置和无关大文件。读取真实提交 ID，不预填“已提交”。仓库策略或权限不允许提交时如实记录，不让这一点阻止其他交付。

## PROJECT_STATE.md 的最小结构

在项目内维护以下信息，不将机器特定绝对路径写入可复用 skill：

```markdown
# 项目状态
- 本轮目标/当前阶段/完成标准：
- 引擎与渲染器、目标平台、启动与测试命令：
- 已可玩的流程与入口：
- 已确定的视觉、动画尺度和声音规则：
- 关键模块与数据/存档版本：
- 最近用户反馈及对应回归场景：
- 验证证据：通过 / 失败 / 未验证，时间及日志/画面路径：
- 当前构建路径、源码对应关系、最后成功运行：
- 真实提交 ID / 未提交状态：
- 重要缺口、阻塞原因与下一步：
```

恢复任务时先比对实际工程与记录；旧记录可能过时。最终回答提供实际启动路径、完成内容、验证结果与剩余限制，避免以功能清单代替验收结论。

## 本 skill 的情境自检

修改此 skill 后，用以下请求检查决策是否合理；这属于规则审阅，只有真实执行了测试任务才可声称行为测试通过。

1. “从零做一个温馨精灵游戏”：新目录，采用默认方案，视觉样片后完成闭环及首版范围，最终导出复验。
2. “继续现有游戏完善并测试”：核对当前文件和用户已认可的反馈，不新建替代工程，不覆盖真实存档。
3. “主角走路忽大忽小”：查图集、alpha、注册点、共享比例和运行时缩放，以连续移动验证，不能每帧拉齐外接框。
4. “宠物平移，而且奔跑比站立大”：同时处理真实步态、跟随状态和跨图集身体尺度，验证起停、转向、碰墙与其他物种。
5. “夜晚再柔和点，白天保持原样”：定位夜间脚步与混音，不启用夜间 BGM，不重置用户音量；真实试听或明确标注未试听。
6. “核心玩法完善了吗”：基于目标链、选择、成长、经济和实际测试评估，不因为有背包/战斗/图鉴就认定完整，不自动开始大改。
7. “做一个 Godot 解谜游戏”：沿用自主制作、画面和交付流程，不加入精灵捕捉的默认产品规则。
8. “导出/GUI 启动被拒绝”：推进可做工作，准确记录未验证项与具体阻塞，不绕过拒绝，不虚构已运行。
